# تقرير اختبار الميزات

تاريخ التنفيذ: 2026-11-09. الفرع: `fix/full-stack-contracts`، طلب المراجعة: [#7](https://github.com/oAlfatki/Hospital-Management-System/pull/7).

## نتيجة التحقق

نجح 45 اختبارًا في مجموعة .NET، و24 اختبارًا في مجموعة Playwright، منها اختبار حدود معمارية الفرونت و23 سيناريو متصفح. عدد الاختبارات ليس عدد العمليات: السيناريو الواحد يتحقق من عدة طلبات وحالات. نجح فحص TypeScript وبناء الفرونت وبناء الحل بوضع Release. بناء الباك يحتوي 37 تحذيرًا، خصوصًا nullability؛ نجاح البناء لا يعني خلو الكود من التحذيرات.

الاختبارات تستخدم API حقيقيًا وقواعد SQLite مؤقتة، والمتصفح يتعامل مع الفرونت والباك معًا. اختبار عرض فشل الشبكة وحده يعترض الطلبات عمدًا للتحقق من واجهة الخطأ. بيانات الاختبار منفصلة عن بيانات المستشفى.

## المعمارية

- الباك: `HSMAPI → HSMBusiness → HSMDataAccess`. Controllers تستدعي الخدمات الأصلية، والقواعد في خدمات Business، وEF والاستعلامات والمعاملات في Repositories. بقيت DTOs وMappers وResultPatern في مواضعها الحالية.
- الفرونت: الصفحات والمكونات تستعمل hooks/services، والخدمات تستعمل API clients والمحوّلات؛ النقل HTTP في ملفات API والإعداد المشترك.
- ثلاثة اختبارات للباك تفحص اعتماد Controllers، وعدم إدخال HTTP/EF إلى Business، وعدم اعتماد DataAccess على الطبقات الأعلى أو كشف DbContext كحقل عام.
- اختبار الفرونت يفحص استيراد HTTP المباشر خارج ملفات API والإعداد، واستيراد ملفات API من الصفحات والمكونات وhooks/providers. هذه حواجز انحدار محددة وليست إثباتًا آليًا لكل مسؤولية ممكنة.
- أُصلحت ثلاثة تجاوزات في الفرونت: Dashboard، وAuthProvider، وتعديل القسم. أُعيد توصيلها عبر طبقات الميزة القائمة.

## استكمال التعديل والحذف والبحث

المراجعة السابقة لم تكن إثباتًا لاكتمال CRUD في الشاشات؛ هذه الجولة أكملت العمليات الناقصة واختبرتها من الواجهة والـAPI.

| الشاشة | البحث | التعديل | الحذف |
| --- | --- | --- | --- |
| المرضى | الاسم والمعرّف وبيانات التواصل وفق الفلاتر الحالية | البيانات والحالة | Admin، مع تأكيد ومنع الحذف عند وجود سجلات مرتبطة |
| الأطباء | الاسم والمعرّف والتخصص والقسم والتواصل | البيانات والقسم والحالة | Admin/Management، مع حماية المواعيد ورئاسة القسم |
| الأقسام | الاسم والمعرّف والوصف واسم الرئيس | الاسم والوصف والرئيس | Admin/Management، مع حماية الأقسام المرتبطة |
| المواعيد | المريض والطبيب والمعرّفات والتخصص والتاريخ والحالة | المريض والطبيب والتاريخ والوقت والمدة؛ مع فحص التعارض | Admin، مع تأكيد، ويشمل المواعيد الملغاة |
| الفواتير | الفلاتر الحالية للمريض والفاتورة | المريض والبنود والضريبة والخصم والاستحقاق قبل أي دفعة | Admin؛ الفاتورة ذات الدفعات محمية |
| الموظفون | الاسم والمعرّف والبريد والدور والقسم والتواصل | البيانات والدور والحالة وكلمة المرور | Admin؛ يمنع حذف النفس والحساب المرتبط بنشاط |
| السجلات الطبية | البحث الحالي بالمريض والتشخيص | المحتوى والحالة مع تاريخ الإصدارات | Doctor/Nurse؛ تأكيد وحماية بإصدار السجل الحالي، مع تسجيل الحذف في التدقيق |
| الإشعارات | البحث وفلاتر القناة والحالة | نص الرسالة وقناة الإشعار المعلّق غير المرسل | للإشعار المعلّق غير المرسل فقط؛ لا يُسمح بتغيير تاريخ التسليم أو الحالة يدويًا |
| التدقيق | البحث والفلاتر والتصدير | للقراءة فقط | غير متاح لحفظ أثر العمليات |

الحذف نهائي للسجل المحدد، ويعرض تأكيدًا قبل التنفيذ. حذف سجل طبي يزيل أيضًا تاريخ نسخه المضمّن؛ الأرشفة متاحة للإبقاء عليه. البحث يعمل على كامل البيانات المحمّلة قبل الترقيم، ولا يُدّعى إضافة pagination/search على الخادم.

أُضيفت ثمانية سيناريوهات متصفح: تأكيد/إلغاء حذف مريض، بحث وحذف طبيب وقسم، بحث وحذف موظف، البحث والتعديل الكامل والحذف للموعد، تعديل بنود الفاتورة وحذفها، حماية الفاتورة المدفوعة في الواجهة، تعديل وحذف إشعار معلّق، وحذف سجل طبي. أُضيفت ستة اختبارات API متعددة الحالات للتحقق من هذه العمليات والقيود، ووُسّع اختبار الأدوار الخمسة ليشمل المسارات الجديدة. جميع الخدمات الجديدة داخل HSMBusiness القائمة، والاستعلام الجديد الوحيد الخاص بارتباطات المستخدم داخل UserRepository؛ لا طبقات أو معماريات جديدة.

## الأعطال التي كشفها الاختبار وأُصلحت

فشلت اختبارات CRUD القديمة الخمسة أول تشغيل. عولجت الأخطاء في الملفات والطبقات الأصلية:

- Person: نجاح زائف بعد الإنشاء وعدم إرجاع المعرّف، وفحص التكرار بشرط AND بدل OR، وتحديث قبل استكمال التحقق.
- Employee وServiceCategory وReport: توليد معرّفات عند الإنشاء وإرجاع المعرّف الفعلي للعميل.
- Controllers قديمة: تغليف CreatedAtRoute داخل Ok بدل إرسال استجابة الإنشاء الصحيحة؛ قراءة ServiceCategory كانت تعيد نصًا بدل DTO.
- ServiceCategory وBillService: تعديل كائن جديد مع وجود كائن متتبع أدى إلى أخطاء تتبع EF؛ صار التعديل على الكائن المحمّل.
- BillService: كان يبحث عن معرف الخدمة في جدول الفئات بدل جدول الخدمات الطبية.
- CSV التدقيق: معالجة الفواصل والاقتباسات والأسطر بدل كسر الأعمدة.
- فشل الخروج: إظهار رسالة مفهومة بدل رفض Promise غير معالج.

عُدلت اختبارات المتصفح أيضًا لتختار البيانات بالاسم بدل ترتيب الخيارات، وتبحث عن السجل عبر الصفحات، وتقارن لوحة التحكم بالإجمالي الفعلي بدل افتراض قاعدة فارغة. هذه تصحيحات لعزل الاختبارات وليست أعطالًا إضافية في المنتج.

## حدود النتيجة وما لم يُختبر

1. لم تُنفذ المجموعة على SQL Server فعلي. نجح فحص نموذج SQL Server وتوليد المخطط وعلاقات المفاتيح وإعداد التزامن، لكن تشغيل حاوية SQL Server تعذر بسبب امتلاء مساحة Docker. أُزيلت الصورة التي نُزّلت لهذا الاختبار. SQLite لا يثبت سلوك الأقفال والترحيلات والتزامن على SQL Server؛ يلزم تشغيل الاختبارات على قاعدة SQL Server معزولة قبل اعتماد النشر. يدعم مصنع الاختبار متغير `HMS_TEST_SQLSERVER_CONNECTION` لهذا الغرض، لكنه لم يُتحقق من هذا المسار على خادم فعلي.
2. لم يُختبر SMTP/SMS أو تسليم خارجي حقيقي؛ المتحقق منه حفظ الإشعار في قائمة الانتظار فقط. لا يوجد مزود إرسال مهيأ في هذه البيئة.
3. لم تُنفذ ترقية بيانات مستشفى قائمة أو اختبارات حمل أو أجهزة ومتصفحات متعددة. تشغيل المتصفح كان Chromium على Linux، مع عرض مكتبي وعرض هاتف محاكى.
4. APIs القديمة المذكورة لا تملك شاشات مقابلة في SPA الحالية. كتالوج MedicalServices لا يوفر CRUD API في المشروع الحالي؛ استُخدمت بيانات تهيئة اختبارية للتحقق من BillService. لا يُدّعى اكتمال واجهات هذه الوحدات.
5. ليست هذه شهادة بأن كل حالة إنتاج ممكنة تعمل؛ الجدول يسجل السيناريوهات التي نُفذت فعلًا وحدودها.

## إعادة التنفيذ والأدلة

من جذر المستودع:

```bash
dotnet build HospitalManagement.sln --configuration Release
dotnet test tests/HSMAPI.Tests/HSMAPI.Tests.csproj --logger "trx;LogFileName=features.trx"
cd "src/frontend/Hospital-management-system v3"
npm ci
npm run lint
npm run build
npx playwright install --with-deps chromium
npm run test:e2e
```

مصادر الاختبار: `tests/HSMAPI.Tests/ArchitectureTests.cs` و`WorkflowTests.cs` و`FeatureApiTests.cs`، و`tests/e2e/architecture.spec.ts` و`features.spec.ts` و`workflows.spec.ts` داخل الفرونت.

تنتج مجموعة .NET ملف TRX داخل `tests/HSMAPI.Tests/TestResults/`، وينتج Playwright تقرير JSON داخل `test-results/results.json` وصورًا/آثارًا عند الفشل. ترفع GitHub Actions الأدلة ضمن artifact باسم `feature-test-evidence` حتى في حال فشل التحقق. النتائج المتولدة مستثناة من Git، ومصادر الاختبارات محفوظة للمراجعة وإعادة التشغيل.
